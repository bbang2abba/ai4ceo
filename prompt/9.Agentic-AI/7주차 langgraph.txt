🧩 RAG 구성
ref.py 파일처럼 구성을 한다. side bar에서 선택하도록 한다.
embedding을 할때, pdf document를 요약을 해서 vectorDB에 저장
각 파일에 대한 요약을 gpt-5-mini 로 해서 요약문을 만들어서, 이를 vector db에 저장한다. 
여러 개의 파일이 들어오면 각 내용을 요약해서 요약문 화일에 추가한다.
따라서, 요약문은 전체 vector db에 1개만 존재한다.   

🧩 전체 Workflow 구성
1. query_routing_node


infinite loop 방지
	infinite loop를 방지하기 위해 routing switch를 구현한다. routing switch는 여러개의 routing 이름이 들어갈 수 있다.  
	routing switch에 내용이 있으면 같은 node로 보내지 않는다. 
	routing swith가 비어있다면 향후 routing이 결정되면, 그 routing의 이름을 add 한다. 
	routing을 결정하면 routing switch에 어디로 가는지를 적는다.

역할: 사용자의 질문을 분석하여 다음 중 한 곳으로 라우팅:

gpt5-mini 가 질문을 읽고 routine을 결정한다.

일단 vectordb의 요약문은 읽는다 그리고 다음 routing을 결정한다. 

검색이 필요 없는 질문 → llm_node
뉴스/주가/날씨 등 실시간 검색 → internet_search_node
요약문을 읽어서 유사하면 → query_rewriting_node

판단 기준:

LLM이 답변할 수 있으면 llim_node
실시간성 강하면 internet_search_node
불확실하면 일단 query_rewriting_node 로 보내고 → RAG 시도 → 실패시 다른 경로로 routing한다. (routing switch활용)

2. query_rewriting_node
사용자의 질문을 바탕으로 의미를 유지하면서도 서로 다른 완전한 문장을 5개 생성
출력된 문장은 retrieve_node로 전달

3. retrieve_node
입력된 5개의 query 각각에 대해 FAISS 기반 vector search를 병렬 수행

검색 설정:
ensemble retriever 사용 (BM25:Similarity = 4:6 비율)
각 query당 결과 chunk는 5개씩 

4. re_ranking_node
총 25개의 chunk를 받아, 원래 질문과 비교해 가장 적절한 5개 선정

평가 기준:

원래 사용자가 질문한 내용을 보고, 그에 대한 답변을 할 수 있는 내용인지를 판단한다. 
답변에 대한 정보를 많이 포함하고 있는 순서로 상위 5개 chunk만을 llm_node로 전송한다

만약 모든 결과가 부적절하다고 판단되면 → 다시 query_routing으로 전송

단, RAG가 아닌 다른 경로 (llm_node or internet_search_node)로 보내야 무한loop 방지할 수 있다.

5. llm_node
2가지 역할:

query_routing에서 들어온 단답형 질문에 대해 직접 답변

re_ranking에서 정제된 5개 문서를 기반으로 응답 생성

5개 문서를 요약하여 1개의 응답으로 종합

6. internet_search_node
사용자의 질문을 받아 Perplexity API를 통해 실시간 검색

결과를 relevance_check_node로 전달

Perplexity 코드 예시 참고:


    from langchain_perplexity import ChatPerplexity
    llm = ChatPerplexity(api_key=perplexity_api_key)
    response = llm.invoke("이정후의 오늘 경기결과는?")
    print(response.content)


7. relevance_check_node
llm_node에서 생성한 응답과 원래 질문을 비교하여 답변 적합성 평가

기준:

답이 있다고 판단되면 → 사용자에게 출력

답이 없다고 판단되면 → 다시 query_rewriting 노드로 전송

단, 점수(score)보다는 **"정답 포함 여부"**로 판별

🧪 디버깅 및 로깅 요구사항
노드	출력
전체 플로우 시작 시	print("===================")
query_routing	들어온 질문과 라우팅 방향 로그
query_rewriting	원 질문과 생성된 5개의 문장 출력
retrieve	각 query에 대한 vectorDB 결과 5개씩 출력
re_ranking	총 25개 중 최종 선택된 5개 출력
relevance_check_node	질문, 답변, 판단결과(yes/no) 출력
internet_search_node	질문 및 검색결과 내용 출력

💡 그 외 주의사항
항상 최신의 라이브러리를 사용하는지 Context7 MCP server로 검증한다
vectorDB 검색 시 반드시 invoke()를 사용 (get_relevant_documents()는 사용하지 않음)

pdf file을 vector db에 저장할 때, 전체 내용을 간단하게 요약을 한다. 
여러개의 pdf file이 들어오면 각각 요약을 한다. 
그리고 그 내용을 vectordb 저장해줘. 그러면 query router가 질문이 들어오면 항상 vector db에서 
요약문을 읽고, routing 판단을  하는 거야.  


검색용 retriever는 BM25 + Similarity 기반 앙상블 구조
최종 응답 전에 반드시 relevance_check_node를 통과해야 함
